# 译文决策与现有实现映射

## 决策矩阵

对每个英文 job 先确定 `correct_cn`，再作决定：

| 条件 | 业务动作 | `sync-cn` 交互映射 | 数据语义 |
|---|---|---|---|
| 文件译文有误，数据库当前绑定正确 | 修改文件，然后以库中为准 | `keep` | 不改 `words` 或绑定；生成结果采用库中值 |
| `correct_cn == cn_in_mysql` | 以库中为准 | `keep`；若文件本就相同则自动 matched | 保持当前记录和关联 |
| `correct_cn == other_cn_in_mysql` | 仅修改关联 | `add` | `apply_sync_batch` 按 `(en, cn)` 复用目标记录，并将当前 `(file, uid)` 重绑到该 `word_id` |
| 正确译文应替换当前记录的所有合理用例 | 修改现有译文 | `modify` | 更新当前 `words.id`；其所有关联都会看到新译文 |
| 正确译文仅适用于当前上下文，或现有记录仍有其他合理用例 | 新增独立译文 | `add` | 新建或复用 `(en, cn)`，并精确绑定当前 `(file, uid)` |
| 无法可靠确定正确译文 | 需人工确认 | 不执行 | 保留证据和候选，不猜测 |

“仅修改关联”和“新增独立译文”在 CLI 中都使用 `add`，区别在于目标 `(en, cn)` 是否已存在；写入层会自动复用已存在记录。不得为了实现“仅修改关联”而选择 `modify`。

## 无需用户决策的内建自动规则

以当前 `/data/5e-translator/app/cli/sync_from_cn.py` 的 `classify_alignment` 为准，以下分类直接执行，不进入普通冲突裁决；记录即使为 `proofread=1` 也不逐项询问：

- `missing`：当前 job 没有 `sql_id`，或仅命中需要补全的 `tag_sync_required` fallback。自动新增或复用完整 `(en, cn)` 记录并绑定当前用例。
- `matching`：库中译文与文件译文完全一致。自动保持译文并补齐/重绑精确用例。
- `auto_keep`：文件值等于英文原文，或库中值与文件值仅单双引号字形不同。自动以库中为准，不修改 `words.cn`。
- `auto_modify`：库中值与文件值的标签外文本完全相同，并且差异只发生在一个或多个完整 `{@...}` 标签内部。自动选择 `modify` 更新数据库；已校对状态保持不变，无需逐项询问。
- 同一 `words.id` 已在本批中确定修改为同一目标值，后续位置自然获得相同译文时，自动沿用 `modify`，不重复询问。

自动规则只消除用户决策，不消除结构安全检查：中英文必须成功对齐；同一 `words.id` 若对应多个不同文件目标值，必须停止自动修改并转为冲突处理；标签不完整、标签外文本也变化、标签数量/骨架不同均不得冒充 `auto_modify`。预演报告应列出各自动分类及理由，但不要逐项请求批准。

### 普通 `modify` 的前置硬性检查

对没有命中上述内建 `auto_modify`、而是在普通冲突中拟 `modify` 的 `words.id`，必须完成两步检查，不允许只凭语义或频次直接选 `modify`：

1. 查该 `words.id` 在 `word_usage` 的文件分布（`SELECT file, COUNT(*) FROM word_usage WHERE word_id=%s GROUP BY file`）；
2. 逐一确认分布中每个文件的当前内容是否已显示拟改值（grep 该文件）。

结论：全部文件已显示新值（含用例仅在本目标文件的记录）→ 允许 `modify`；任一文件仍显示旧值（典型：目录索引 `books.json` 复制的章节名、尚未同步的同源段落、其他书里同一实体的旧名）→ 降级为 `add`（scoped 新增/重绑），并在最终报告把该文件列为遗留修改事项。

## 标签重排序错位（假冲突）

`align_manual_translations` 的标签子对齐按“同一标签类型内的出现顺序”匹配英文子值与中文子值。中文为语法需要调换标签顺序时，位置匹配会整体错位。例：英文 “{@creature skeleton} riding {@creature warhorse skeleton} or {@creature wight}” 译作 “骑着{@creature 骷髅战马}的{@creature 骷髅}或者{@creature 尸妖}”，会产生 Skeleton→骷髅战马、skeletons→战马骷髅、Warhorse Skeleton→尸妖 等全错配。

识别特征（同时满足前两条即高度可疑）：

- 冲突项是标签子任务：`key_path` 以 `/creature[N]`、`/item[N]`、`/spell[N]` 等结尾；
- en 是常见实体名（尤其核心怪物/物品名），cn_file 却是语义不相关的另一实体；
- 该 en 对应 `words.id` 的用例遍布几十个文件、数百处（核心术语特征）。

处理：一律 `keep`。库中绑定正确、文件父串显示也正确（渲染以父串完整译文为准），错位只发生在子对齐层面；`modify` 会把高用例核心术语全局改成错位值。用父串（含该标签的完整句子）的库中译文与文件一致性确认无误即可放行。

## 已校对普通冲突门禁

当普通 `conflict` 中拟执行 `modify` 的 `words` 记录为 `proofread=1` 时，每条记录都必须单独提交用户裁决。命中上一节内建 `auto_modify` 的记录不适用本门禁，即使已校对也直接修改。普通冲突提问前提供：

- `words.id`、英文、当前已校对译文和拟改译文；
- 修改原因，以及术语库、不全书、`data` 频次和当前上下文中的关键证据；
- 该记录全部 `word_usage` 的数量和代表位置，说明全局影响；
- 不修改时可选的 `keep`、新增独立译文或跳过方案。

一次只询问一个 `words.id`，收到明确肯定答复后才把该项标记为允许修改，再询问下一项。不得用“是否批准以上全部修改”、目录级写库授权、此前相似记录的答复或沉默代替逐项确认。同一 `words.id` 在多个位置出现时只询问一次，但必须在该次询问中列全影响范围。

拒绝、含糊或暂缓均视为未授权普通 `modify`。此时重新选择 `keep`、新增独立译文或跳过，并确保磁盘文件与预期结果一致。不要对已被 `sync-cn` 分类为 `auto_modify` 的项目再次询问。

## 判断正确译文

依次权衡：

1. 明确适用于该语境的术语库规范；
2. 当前句及其实体、章节、规则含义；
3. 已校对且上下文相同的数据库/文件用例；
4. 全库译文分布。

分别统计不全书语料和 `data` 全库；至少记录每个中文候选的次数、涉及文件数和代表性位置。重复模板或单一文件大量重复可能造成虚高，应同时看“出现次数”和“文件数”。不同英文同形词、专名/普通词、标签内部值、版本差异不可仅凭字符串合并。不全书取用顺序：本地语料 `/data/DND5e_chm` 优先（`书名/章节/条目.htm` 结构，可直接检索），本地不可用退化到 `BuquanshuSearcher` 网络检索；两者都不可用时才标记证据缺失并询问用户，不能把 `data` 统计改名为不全书统计。

以下情况不能自动依多数票：

- 多个候选接近，或多数译文来自同一重复模板；
- 术语库与多数译文冲突；
- 当前上下文明显要求专名、规则定义或不同词义；
- 只存在未校对候选；
- 标签结构、标点或英文原文版本不一致。

## `sync-cn` 的已知行为

- 单文件或递归目录均可；未给 `--cn` 时只会把英文路径中的 `data-bak` 替换为 `data`，本技能通常显式传入两边路径。
- 命令没有 dry-run，也不会只处理 Git diff；整份文件里的 missing、matching 和自动决策都可能写入或重绑，必须在执行前用只读分析器完整盘点。
- 中英文结构必须能通过分析器 marker 安全对齐。
- 文件值等于英文原文，或仅引号字形不同，会自动保留数据库值；仅标签内部内容不同会自动修改现有记录。若这与审查结论不符，先停止，不盲从自动动作（坏值情形的修正路径见下方专节）。
- 上述自动标签修改不会询问用户；这是预期行为，目标记录即使已校对也直接修改并保留校对状态。
- 同一 `words.id` 在本次同步中不能被修改成两个不同值。
- `words` 与 `word_usage` 对单文件在同一事务写入；目录不是全局事务。
- 新增项默认为未校对；修改会保留原记录的校对状态。
- 同步后会重新分析英文并从数据库生成中文；只有生成对象与预期一致才算验证通过。
- 验证失败发生在写库之后。此时不要覆盖中文文件，应报告首个差异并检查数据库状态。
- CLI 的 `added` 同时包含新建记录和复用已有 `(en, cn)` 后重绑；最终分类必须依赖执行前后查询，不能照抄汇总数字。
- `word_usage` 存在旧 uid 格式的陈旧残留行（`legacy:<id>`、带 `.0` 等尾缀），与当前格式同位置并存；唯一键 `(file, uid)` 按完整 uid 判定，当前分析器/生成器只使用新格式，旧行不影响结果，也不是重绑失败的证据。

### auto_keep 保留坏值的修正路径

文件值==英文（如用户把表格单元改成 `A ♦` 这类标准记法）触发 auto_keep 时，若库中值本身是乱码——双重转义的 `\u2007`、丢失牌点数、颜色参数被当显示文本、表情符号残留等——按自动保留执行会在下次再生成时回退用户的修复。处理：

1. 同步前以直接 `UPDATE words SET cn=<文件值> WHERE id=<id>` 逐条修正；这是写库动作，须列入决策清单并授权。生产库已存在 `cn == en` 的记录（如序数 "2nd"），不会因 cn 等于英文而被判定为未翻译；
2. 重跑预演：这些条目从 `auto_keep` 变为 `matching`，各分类计数随之变化，清单需同步更新；
3. 再执行同步；内建的逐字段验证会确认生成值等于磁盘值，作为该修正的验收。

## 安全检查

- 决策前保存只读证据；不要通过试写数据库来探索结果。
- 使用参数化查询或现有数据库类，不拼接用户输入到 SQL。
- 不输出数据库密码、连接串或 `.env` 内容。
- 批量目录执行前提醒用户它可能产生部分成功；执行后按文件核对成功、失败和跳过数。
