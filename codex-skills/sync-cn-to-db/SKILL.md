# 同步中文译文到数据库

目标是让数据库和指定中文 JSON 表达经过核实的正确译文，并证明正常 `translate` 流程可以复现结果。不要把“文件中的新值”直接视为正确答案。

## 边界与准备

- 用户必须指定 `data` 下的单个 JSON 或目录。把路径解析为绝对真实路径，确认没有通过符号链接逃出当前仓库的 `data/`；仅处理该范围。
- `/data/5e-translator` 是执行目录；先确认其工作树和配置可用，不改动其中代码。
- 执行环境事实：必须用 `/data/5e-translator/.venv/bin/python` 且工作目录为该仓库根（否则 `dotenv`/`logger_config` 导入失败）；直连数据库时 `MySQLDatabase(**{k.lower(): v for k, v in DB_CONFIG.items()})`（配置键是大写）；分析器处理数千 job 的文件一遍需数分钟，完整流程约需跑 3–4 遍（预演、改动标记、同步内含两遍），预演与执行应尽量合并进同一进程。
- 中文路径通常映射到同相对路径的 `data-bak` 英文文件。若不能唯一映射，停止并询问，不猜路径或模式。
- 根据文件类型选择 `5et`、`splited`、`homebrew`、`plu` 或 `ua` 模式；不能确定时从仓库现有命令、相邻文件和分析器调用中核实。
- 数据库写入和文件改写是两类独立变更。先完成只读分析并展示决策清单；用户尚未明确授权实际同步时，在执行前取得确认。不要把创建本技能或请求“分析”当成写库授权。指名路径的同步请求（如“同步 data/book/x.json”）即视为标准流程的写库授权；但三类越轨动作仍须在清单中单独列出并取得明确确认：绕过 `sync-cn` 自动逻辑的直接数据库修正、用例遍布多个其他文件的大范围全局 `modify`、与术语库规范冲突的文件值。已校对（`proofread=1`）记录只有在普通冲突中拟 `modify` 时才受第 7 步逐项询问门禁约束；内建自动分类不询问。
- 开始前阅读 [references/decision-guide.md](references/decision-guide.md)。若实际代码与参考冲突，以当前代码为准并指出差异。

## 工作流

1. 用 `git diff -- <中文路径>` 定位用户改动；同时加载完整中文 JSON 和对应英文 JSON。不要把无关的既有工作树改动纳入范围。判定“哪些任务在 diff 内”必须用 `git show HEAD:<中文路径>` 加载 HEAD 树与磁盘树做结构化叶子对比，再经对齐结果的叶子路径映射到 job UID；不要用“文件值是否出现在 diff 的 `+` 行”做字符串匹配——diff 原始行是 JSON 转义形式（如 `\u2014`），与解码后的字符串不匹配，会大量漏判。
2. 从现有分析器产生 job/UID 映射，将改动定位到英文原句、文件、`key_path`、上下文类别和数据库记录。优先复用 `/data/5e-translator/app/cli/sync_from_cn.py`，不要另写一套 JSON 对齐器。
3. 对每个变化的翻译建立证据集：
   - 术语库中的规范译名与适用范围；
   - 当前文件的上下文、实体、标签和相邻段落；
   - 数据库中同一英文的全部中文候选、校对状态及 `word_usage`；
   - 5E 不全书语料中该英文的全部可定位译文。优先使用本地语料 `/data/DND5e_chm`（按 `书名/章节/条目.htm` 组织，与线上站点同构，可直接 `grep -r` 或脚本检索；使用前确认目录存在且结构相符）。本地不可用再退化到网络检索：`/data/5e-translator/app/core/agent/buquanshu_search.py` 的 `BuquanshuSearcher`（远程检索 API，不是本地目录，勿再向用户索要“本地不全书根目录”）。术语/实体参照仍可复用 `codex-skills/5etools-buquanshu-proofread/scripts/lookup_reference.py`。无论哪种来源，都不能拿 `data` 全库冒充不全书统计；
   - `data` 全库中该英文在各上下文实际对应的中文，作为额外工程证据。对不全书与 `data` 分别统计每种译文的出现次数、文件数、总数和占比。
4. 频次只决定置信度，不取代语义判断。结合专名、规则术语、书名/版本、大小写、标签显示文本及上下文决定 `correct_cn`；证据冲突或置信度不足时标为“需人工确认”，不得写库。
5. 按参考中的决策矩阵为每个 job 选择动作。先应用 `sync-cn` 当前代码中的内建自动分类；命中自动分类的项目无需用户决策，包括已校对记录。相同 `words.id` 的所有受影响用例仍须一起检查，避免一次全局修改破坏另一处上下文。两条硬性规则：
   - 跨文件检查：对普通冲突中拟 `modify` 的 `words.id`，先查 `word_usage` 的文件分布，再逐一确认分布中的文件当前内容是否已显示拟改值（grep）。全部已显示才允许 `modify`；任一文件仍显示旧值（如目录索引 `books.json`、尚未同步的关联文件）则降级为 `add`，并在报告列为该文件遗留事项。内建 `auto_modify` 不进入此人工裁决流程，但仍须通过同一 `words.id` 目标值碰撞检查。
   - 标签重排序错位：对齐器按位置匹配标签子值，中文为语序调换标签顺序时会产生语义完全错位的假冲突（如 Skeleton→骷髅战马、Wight→骷髅）。标签子任务（`key_path` 以 `/<tag>[N]` 结尾）且 en 为常见实体名、cn_file 是明显不相关的另一实体时，一律 `keep`，用父串完整译文确认文件显示无误即可；详见 decision-guide。
6. `sync-cn` 会分析整个目标文件而非只处理 Git diff。执行前用 `python3 main.py sync-cn ... --preview` 清点该文件中所有 `missing`、`matching`、`auto_keep`、`auto_modify` 和普通 `conflict`，不能只展示手工改动处。预演结果中的内建自动分类直接采用，不询问用户；只有普通 `conflict` 进入证据裁决。若审查发现自动分类的结构前提不成立或出现同一 `words.id` 多目标值碰撞，则停止该项而不是盲目执行。典型的库中乱码例外修正路径详见 decision-guide。
7. 先向用户给出紧凑清单：位置、英文、文件译文、当前绑定译文、其他库中候选及频次、不全书与全库文件译文频次、建议正确译文、动作、理由和影响范围。另列出未在 diff 中但命令会写入或重绑的项目。
   - 仅对普通 `conflict` 中拟修改 `proofread=1`（已校对）现有记录的项目，提供具体修改原因、当前值、拟改值、证据和全部受影响用例，然后按 `words.id` 逐个询问；一次只询问一项并等待答复，不得合并或批量确认。
   - 命中内建 `auto_modify` 的已校对记录是该门禁的明确例外：在清单中说明命中的自动规则后直接修改数据库，不询问用户。未命中自动规则且未获明确肯定答复的已校对普通冲突，不得选择 `modify`。
8. 获得文件改写授权后，先修正所有被判为“修改文件”的中文 JSON，使磁盘值等于 `correct_cn`，再重新解析 JSON、重跑预演并更新清单。`keep` 不会修正磁盘文件，不能用 `verified=true` 掩盖文件仍错误。
9. 写库前记录受影响 `words` 行及其全部 `word_usage` 的 ID、原值与绑定，形成可审核的恢复清单；这不是自动回滚授权。获得数据库写入授权后，从 `/data/5e-translator` 运行现有入口：

   ```bash
   python3 main.py sync-cn --en <英文文件或目录> --cn <中文文件或目录> --mode <mode>
   ```

   在交互冲突中，严格按照已经确认的清单选择；出现未分析的新普通冲突就停止该项并重新审查。新出现的已校对普通冲突必须回到逐项说明和询问门禁；内建自动规则仍直接执行。对“仅修改关联”，选择能复用目标 `(en, cn)` 并重绑 `word_usage` 的 `add`，不要更新旧 `words` 行。
10. 检查命令汇总和失败列表。目录模式是逐文件提交：某文件失败不会回滚已成功文件；验证也发生在提交之后。失败时停止后续扩大写入，保留恢复清单，报告已提交状态并请求用户决定是否补偿，禁止擅自反向写库。
11. 执行后查询受影响行和绑定，按执行前候选存在性区分“真正新增”与“仅修改关联”；CLI 的 `added` 汇总不能区分两者，可用新记录 id 区间（比较执行前后 `MAX(id)`）统计新建数。核对绑定时注意 `word_usage` 存在旧 uid 格式的陈旧残留行（`legacy:<id>`、带 `.0` 等尾缀）：唯一键按完整 uid 判定，当前分析器只产生新格式，同位置出现旧行不代表“重绑失败”。用 `git diff --check -- <中文路径>`、JSON 解析和必要的数据测试验证文件；以 `sync-cn` 的重新分析/重新生成验证作为数据库结果的必需验收。不要自动提交 Git。

## 输出约定

最终报告分别列出：文件改动、数据库新增、全局修改、仅重绑关联、保留库中、待人工确认、失败/跳过文件，以及验证结果。对每个“修改现有译文”明确给出受影响用例数量；已校对自动修改项列出命中的规则，已校对普通冲突列出修改原因和用户逐项裁决；对多数票判断给出计数，避免只写“更常见”。
